# JuiceFS 性能提升点全量总结

> 范围：production/ 和 production/prod-deploy/ 中全部任务书、报告和周报
> 日期：2026-09-12
> 整理人：GLM52

---

## 一、已进入生产交付配置的改进

### 1. JuiceFS 随机写 FlushTo 异步补派发修复（B-catchup 补丁）

- **发现**：JuiceFS v1.3.1 在 256K FUSE 下 randwrite 从约 3000 MiB/s 塌至 551 MiB/s。排查发现异步 `prepareID` 与 `writeChunk` 竞争同一 `fileWriter` 锁，满 block 的 `FlushTo` 被跳过且 `SetID` 后无补派发，导致缓冲排水自锁。
- **处理**：保留异步 ID 创建，在 ID 就绪后按条件补 `FlushTo`，避免用户 `WriteAt` 返回强制依赖 slice 分配。
- **收益**：randwrite 恢复至正常平台（~3000 MiB/s 量级）。v1.4.1 原版同样存在此缺陷（551 MiB/s），必须携带补丁才能交付。

### 2. Ceph 客户端 `ms_async_op_threads=8`

- **发现**：高并发 randread 跨挂载 CV 高达 20%，不同挂载间 15%–40% 抽签波动。排查发现默认 3 个 msgr worker 下，6 条 OSD 数据连接建连落位不均衡，单个 worker 打满而其他欠载。
- **处理**：通过客户端私有 `ceph.conf` 将 `ms_async_op_threads` 从默认 3 增至 8（≥ OSD 数 × 1.33），不改集群级配置。
- **收益**：randread 好档对好档保守 +37.4%，交付基线相对 03-10 阶段 +44.7%；跨挂载 CV 从 20.01% 降至 0.79%。写侧无代价（+0.7%，噪声内）。

### 3. FUSE `--max-fuse-io 256K`

- **发现**：默认 FUSE 请求粒度小于 256K，4 MiB 应用 I/O 被 FUSE 拆成过多碎片，GET/IO 比率高、RX 放大严重。
- **处理**：设置 `--max-fuse-io 256K`，使 FUSE 请求粒度与 block size 对齐，4 MiB I/O 的 FUSE 拆分数从 32 减至 16。
- **收益**：单流 seqread/seqwrite 观察到约 +13%/+20%；GET/IO 从 1.62 降至 1.15，RX 放大从 2.30× 降至 1.22×。多流项无同幅收益，是交付基座的一部分。

### 4. JuiceFS v1.4.1 + B-catchup 版本替代 v1.3.1

- **发现**：需评估 v1.4.1 能否替代交付基座 v1.3.1。v1.4.1 原版存在与 v1.3.1 相同的随机写缺陷（551 MiB/s），必须携带补丁。
- **处理**：对 patched v1.4.1 与 patched v1.3.1 做同集群、同配置、同数据的 40 轮逐轮交替 ABBA 对照（版本选型 + 补证）。
- **收益**：七项差距均在 ±1% 以内（seqread -0.05%、mseqread +0.57%、randread +0.58%、randrw -0.52%、seqwrite -0.28%、mseqwrite +2.96%、randwrite -2.08%），四端点均排除 >5% 退化。元数据格式双向兼容、可回滚。正式批准替代。

## 二、验证有效但未进入通用生产配置的改进

### 5. PG Primary 负载均衡

- **发现**：自然 PG primary 分布严重不均（I_primary=1.40625，分布 10:15:11:11:8:9），randread 存在读负载热点。
- **处理**：在同一 64-PG EC 4+2 测试 pool 上，手工 `pg-upmap` 将 primary 均衡至 I_primary=1.03125（分布 10:11:11:10:11:11），ABBA 对照。
- **收益**：randread +13.67%（3467→3924 MiB/s），同条件极差仅 0.23%。
- **未采纳原因**：收益与特定初始布局相关；在线 pool 使用 `pg-upmap` 可能触发 shard 重排和恢复流量；需关闭自动 balancer 后人工维护，扩容/故障后重算，运维复杂度过高。

### 6. TiKV WAL/Raft 物理路径隔离

- **发现**：randwrite 尾段 CV 高（个别达 12.19%）、W4/W1 低至 0.810，TiKV 的 WAL/Raft 日志与 KV/compaction 共享同一 NVMe，尾段 compaction 排队放大写入延迟。
- **处理**：在同一 fresh 临时 TiKV、同 seed、同负载下，只把 32 GiB WAL/Raft backing 从共享 NVMe 移至 RAM，4 组配对 ABBA。
- **收益**：配对中位 +5.05%（4/4 正向），CV 中位改善 2.36pp，W4/W1 中位提高 0.0694，Raft sync 从 0.22–0.80ms 降至 0.074–0.083ms。
- **未采纳原因**：RAM 不可持久化；带宽收益未过 15% 材料门，D1 仍只达目标 60.10%。同拓扑下把 TiKV 全部存储换 RAM 仅 +0.26%，介质效应量级 0%–3%。真实第二块 NVMe 的带宽收益上界不超过 +5.05%，采购理由只能是稳定性而非带宽。历史 TiKV→fresh 组合差 +25%–30% 的更大因子未被单独拆分。

### 7. 本地读缓存（JuiceFS read cache）

- **发现**：无缓存时 mseqread/randread 后端 Ceph 数据网 RX 接近满载，热数据重复读取全部走远端。
- **处理**：启用 JuiceFS 本地 NVMe 读缓存，按热工作集比例测试 0%/25%/50%/75%/100%/200% 六档容量曲线。
- **收益**：热数据 100% 驻留时，mseqread 从 4.6 升至 34.8 GiB/s（+672%），randread 从 4.4 升至 36.5 GiB/s（+744%）；75% 拐点处 mseqread +173%、randread +233%。
- **未采纳为固定配置**：收益取决于热数据占比和工作集大小，需按业务 I/O 模型选择缓存容量。35–37 GiB/s 是本地页缓存/NVMe 热集路径，不是 Ceph 裸盘带宽。

### 8. writeback 对 randwrite 的短时前台收益

- **发现**：randwrite 无缓存时前台带宽受同步 Ceph 写限制，无法吸收突发。
- **处理**：启用 writeback 模式，测试 20/32/64/128 GiB 四档可用空间的 active-I/O 带宽和排空时间。
- **收益**：active-I/O 带宽从 2642（20 GiB）升至 3849 MiB/s（64 GiB，+45.69%），64 GiB 以上趋于饱和（实测脏数据峰值约 53 GiB）。
- **未采纳为通用配置**：writeback 改变的是前台返回时间，不是长期持久化服务率；180s 持续满压下 128 GiB 在 900s 内仍未排空。适合有持久本地空间、单客户端独占写、突发间有排空窗口的场景。

### 9. 纯读缓存对 randrw 的有条件收益

- **发现**：randrw（50/50 读写）读侧可走缓存但写侧始终走后端，且写操作持续淘汰已缓存读块。
- **处理**：修复此前正式窗递归采样干扰后，在 128×1 GiB 既有热集上测试 32/64/96/128/256 GiB 五档纯读缓存。
- **收益**：只开 128 GiB 读缓存时双方向均值 +12.32%；96 GiB 是 128 GiB 热集的最小平台档（相对 256 GiB 仅低 4.37%）。命中率从 11% 升至 47%，但有效卸载率最高约 24%（命中率只作用于读侧 50%），带宽增幅有限。
- **未采纳为固定配置**：randrw 持续覆盖使已缓存读块失效，W4/W1 仍下降 22%–29%；当前仅登记 96 GiB 为 canary 起点。

### 10. `--max-fuse-io=1M` 对 seqwrite 的正式收益

- **发现**：256K FUSE 下 4 MiB 单流 seqwrite 的 FUSE 写请求被拆成 4×256K，PUT/OSD 完成率受限。
- **处理**：四组 A-B-B-A 交错配对正式验证 `--max-fuse-io=1M` 对 4 MiB seqwrite 的收益，并补测六项兼容性。
- **收益**：seqwrite 几何平均 +14.31%（95% CI [+13.00%, +15.63%]），FUSE 平均写请求从 256K 扩至 1M，PUT/OSD 完成率 +14.5%。
- **未采纳为通用配置**：randwrite 触发回归门（一组 -21.82%），mseqread 非劣未通过（-6.35%/-2.15%）。仅作为顺序写专用挂载的灰度候选，不替换通用 256K 基线。

### 11. 大块读 `max-readahead=32M` + `async_dio + libaio`

- **发现**：20M bs 同步单流读受限于在途 GET 数仅约 4 个；Ceph 后端直接 RADOS QD8 可达 5403 MiB/s，但 JuiceFS 同步单流只到 ~2900 MiB/s。
- **处理**：提高 `max-readahead` 至 32M 将 B4 在途 GET 从 2.3 翻至 4.5（+73–77%）；进一步启用 `async_dio + libaio` 将应用 QD 从 1 提到 8。
- **收益**：libaio QD8 带宽达 5278 MiB/s，越过 H3C 披露的 5149.84 MiB/s。GET 在途量达 15.07。
- **未采纳为通用配置**：改变了应用 I/O 提交语义（异步），FUSE `max_background=50` 在 QD4+ 时已触顶。写侧异步 QD 提高反而降低带宽。适用于特定大块异步读场景。

## 三、关键负向结论（排除了的调优方向）

| 方向 | 发现 | 结论 |
|---|---|---|
| 关闭预读 `--max-readahead 0` | randrw 历史上有矛盾的 +28% 证据 | 严格 A/B 仅 +1.6%，CI 上界 <5%，排除有效收益 |
| EC4+2 → Rep3 后端切换 | 猜测 EC 写放大限制 randread | RADOS 层 EC vs Rep 基本相当（0.80–1.30×），FUSE 才是主瓶颈 |
| 增大 BlockSize 至 4M | 猜测减少 GET 数可提升带宽 | B4/RA8 反而慢 34%，因 readahead 只允许 ~2 个在途 4M GET；RA32 修复后 B4 仍不优于 B256 |
| 读缓存 + writeback 同时开启 | 猜测双缓存叠加收益 | 共用 cache 目录产生竞争，randrw 反而下降 16.88% |
| 单文件异步写提高 QD | 猜测类似异步读可提升写带宽 | QD 1→8 带宽反而从 1350 降至 960 MiB/s，单文件异步写流水线无法转化更高 QD 为有效并发 |
| TiKV 存储介质升级（NVMe→RAM） | 猜测介质是随机写主瓶颈 | 全 RAM 仅 +0.26%，介质效应 0%–3%，主瓶颈在同步元数据事务 |
| `max-downloads` 提高 | 猜测下载并发限制 | 单流在途量仅 4–12，远未触及 200 上限，非瓶颈 |
